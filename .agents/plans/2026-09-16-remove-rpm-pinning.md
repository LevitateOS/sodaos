# Remove RPM pinning (reproducibility requirement + machinery)

## Goal

Dev media builds on demand again. Delete every reproducibility
requirement and all code, lock data, tests, and docs that enforce one:
host RPMs install by requested *name* against current Fedora repos, and
the CoreOS base and upstream ISO resolve live from the stable stream at
build time — always the latest, never a stored version. Everything
resolved is recorded into the per-build bill of materials (`packages.txt`
for RPM actuals, release + digests for the base), which is the only
version record kept. Tool-asset digests (`tailscale-image`,
`installer-tools`, `media-tools`, `go.mod`/`go.sum`) stay pinned: they
are immutable, fetchable forever, and never block a build. Reproducibility
returns after release as qualification-time snapshots, not as pre-release
locks.

## Success Criteria

- `sudo soda-candidate media` reaches exit 0 on current Fedora repos with no
  relock step anywhere in the loop.
- No file in the tree references `packages.expected`, `relock`,
  `host-packages-*.json`, or `coreos-host.json` / `coreos-iso.json` /
  `coreos-qemu.json` (verified by grep).
- The filed bill of materials names the actually-resolved base release +
  digests and the installed RPM set; no input file prescribes a version.
- `go build ./...`, scoped `go vet`, the touched packages' `go test`, and
  `python3 -m unittest discover -s tests/build` are green; Go lint gates show
  zero *new* findings versus today.
- The filed media contains a `packages.txt` bill of materials; evidence
  validation (`matchingReleaseProvenance`) still passes on it.

## Context And Current Facts

- The host image layers Fedora RPMs via `rpm-ostree install $(cat
  packages.list)` (`appliance/host.Containerfile`), then fails the build
  unless `rpm -qa` output byte-equals `packages.expected`
  (`diff -u packages.expected packages.txt`).
- `packages.list` (170 exact NEVRAs) and `packages.expected` (full inventory)
  are generated by `LockHostPackages` (`internal/release/image/complete.go`)
  from `appliance/locks/host-packages-x86_64.json` (`Install`,
  `Inventory`), cross-checked against requested names parsed from
  `appliance/provisioning/base.json` (`PackageInputs` in `prepare.go`).
- `build_host.go` re-checks recorded `packages.txt` against
  `packages.expected`; `build_payload.go:admitHostPackages` hashes
  `packages.expected` into `Payload.HostPackagesSHA256`, which
  `deliver/model.go:235` and `deliver/prepare.go:25` require to equal the
  hash of recorded `packages.txt` (true only when actual == pinned).
- `scripts/relock-host-packages.sh` recomputes pins against live Fedora
  repos; today it refuses all 4 drifted pins (cockpit-ws/selinux 366,
  policycoreutils 3.10-4, all pruned upstream) because no base-compatible
  combination exists on CoreOS 44.20260817.3.2.
- Requested product choice already lives version-free in
  `appliance/provisioning/base.json` + `soda-extensions.service`
  (`rpm-ostree install -y --allow-inactive <names>`, parsed by
  `parseInstallPackages`, bare-name regex).
- Kept pins are immutable and stay: `tailscale-image.json`,
  `installer-tools.json`, `media-tools.json`, `go.mod`/`go.sum`
  (content-addressed digests, fetchable forever, never block a build).
  Release docs mandate no RPM pinning (`docs/architecture/release.md`,
  `docs/development/release.md` contain no pin requirement).
- The base is currently pinned three ways and all three rot: `LoadBase`
  (`internal/release/image/prepare.go:23`) validates `coreos-host.json`
  (release string + both arch digests); `soda-artifacts fetch-coreos-iso`
  downloads the live ISO from `coreos-iso.json` (`docs/guides/media.md`
  documents the table); `coreos-qemu.json` rides along in evidence inputs
  (`bundle.go:isLockInputsPayload`). The assembler consumes the base via
  `base.Images[arch]` (`build_host.go:91`, `build_payload.go:112`).
- Current working tree (uncommitted) holds 5 files from this session; only
  `tests/build/test_host_packages.py` overlaps this plan (its
  `RelockScript` class is deleted with the script; `HostPackages` stays).

## Constraints And Non-goals

- No new machinery except the stream lookup that replaces the three base
  files: no mirror, no snapshot service, no replacement solver, no
  version-range resolver. `rpm-ostree` resolves names at build time.
- No change to what ships: the requested package set is byte-identical
  (same names from `base.json`); only the version resolution floats.
- No release-qualification redesign: evidence fields keep their names and
  digest validation; `HostPackagesSHA256` is re-sourced, not removed.
- Out of scope: pre-existing `errcheck`/`gofumpt` backlogs, aarch64 work,
  the `go` wrapper, TUI rendering, log retention.
- Rollback per unit is `git revert` of that unit's commit; units are ordered
  and independently committable (U2 deletes nothing U3 still calls — the
  split below respects that).

## Key Decisions

1. **Float names, record actuals** (vs snapshot mirror vs scheduled
   relocks). Snapshots need storage machinery; scheduled relocks keep the
   treadmill. Floating matches the pre-release stage; recording preserves
   debuggability. Rejected alternatives die in Constraints.
2. **Delete the lock file entirely** (vs trimming to
   `{CoreOS, Architecture, Requested}`). `Requested` already has a single
   source in `base.json`/units; a trimmed lock would be a second source of
   the same truth inviting re-divergence.
3. **Keep `HostPackagesSHA256` populated from recorded actuals** (vs
   dropping the field). `deliver/payload.go:52` requires a valid digest and
   `matchingReleaseProvenance` gates evidence; re-sourcing keeps both
   working with zero schema change.
4. **The base resolves live; it is never re-pinned.** A fresh pin would
   rot exactly like the old one, so Unit 1 replaces the three base files
   with two live lookups at build time: the stable stream (release +
   live-ISO locations) and the registry (container digests from the
   `stable` tag's manifest index) — validated in memory, recorded into
   the bill of materials. Trust is HTTPS plus content-addressed digest
   use — the same basis on which the build already consumes live Fedora
   repos; no new signature machinery for the dev stage.
5. **Tool-asset digests stay pinned.** They are immutable and never block
   a build; floating toolchains would trade this treadmill for a worse
   one (mysterious breakage from silently newer tools). If that trade
   ever looks wrong, it is a separate decision.
6. **Reproducibility returns post-release as qualification-time
   snapshots.** When qualification exists, the qualifier freezes the
   actually-resolved bill of materials into immutable inputs. Until then,
   no pre-release lock of any kind.

## Recommended Approach

Replace the pin-then-verify pipeline with request-then-record: `Prepare`
already parses version-free names; write those to `packages.list`, let
`rpm-ostree` resolve, keep recording `packages.txt`, and hash the recording
into evidence. Delete everything whose only job was prescribing versions
ahead of the build.

## Work Plan

### U1 — Resolve the base live (replaces all three base files)

The stable stream carries release, live-ISO, and qemu locations but no
container digest (its `images` section is cloud-only), so resolution is
two lookups, both live, both recorded:

- Stream: fetch `streams/stable.json`, take the current build per arch
  from `architectures.<arch>.artifacts.metal.formats.iso.disk`
  (`location`, `sha256`, `signature`) and the qemu disks the same way.
  The release string parses out of the ISO location path
  (`/builds/<release>/`, validated with today's release regex); the
  per-artifact entries carry no release field of their own.
- Registry: resolve `quay.io/fedora/fedora-coreos:stable` to its manifest
  digest (per-arch from the index) over plain HTTPS with stdlib only.
  P1 then pulls the digest-pinned ref through the existing
  `pullResolvedInput` mechanism, so `app-inputs.json` records the base
  container as found-latest evidence like every other image.
- `internal/release/image/prepare.go`: rework `LoadBase` into this
  lookup, returning the existing `Base` shape (`Release`, both arch
  digests, `MetadataURL` = the resolved build's `release.json`).
  Both endpoints (stream URL, registry base) are overridable by
  environment for fixture-based tests. Shape validation stays as strict
  as today, applied in memory.
- Delete `appliance/locks/coreos-host.json`, `coreos-iso.json`,
  `coreos-qemu.json`. `soda-artifacts fetch-coreos-iso` drops `--lock`
  and resolves from the stream (same env override); `ReadCoreOSISO`
  becomes a stream parse. The evidence-inputs entry
  (`bundle.go:isLockInputsPayload`) carries the resolved stream record
  instead of `coreos-qemu.json`.
- `writeBuildRecord` keeps recording `CoreOS` + `Base` — now the live
  resolved values, which is the base half of the bill of materials.
- Probe before relying on it: fresh scratch container from the resolved
  base digest, `rpm-ostree install` the requested names from
  `appliance/provisioning/base.json`; the probe must resolve with no base
  replacement.
- Rewrite `TestBaseLockAndUnsafeOutputRefusal` around the stream path
  (it reads `coreos-host.json` today) plus `coreos_iso_test.go` around
  local fixtures: bad-shape stream, untrusted URL, digest mismatch, and
  unsafe-output refusal.
- Validation: `go test -count=1` on `internal/release/image`,
  `internal/release/build`, `tools/soda-artifacts`;
  `grep -rn 'coreos-host\|coreos-iso\|coreos-qemu\|ReadCoreOSISO'`
  shows only U4's doc lines; probe log shows a clean transaction on the

## Risks / Rollback

- **First unpinned layering surprises** (a name disappears or splits
  upstream): builds fail loudly at `rpm-ostree install`, never silently;
  fix is a requested-set edit in `base.json`, not a solver project.
- **Evidence consumers outside the tree** (dashboards reading
  `HostPackagesSHA256` expecting pre-build values): field name and digest
  shape unchanged; semantics move from "prescribed" to "recorded" — noted
  here, no external consumer is known in-tree.
- **Future qualification wants pins back**: git history retains the lock
  and relocker verbatim; reintroduction is a revert plus a snapshot store,
  explicitly deferred until qualification exists.
- **Stream or registry unreachable, or serving a base our layering
  breaks against:** the build fails loudly at Prepare, never silently on
  stale data; there is deliberately no fallback to stored versions (a
  fallback would resurrect the requirement). Fix is retry or a
  requested-set edit.
- Rollback: `git revert` per unit, in reverse order; U1 revert restores
  the three base files (rebuilds will fail on drift again — that is the
  pre-plan status quo, not a regression).
