# Prepare a Project for Factory work

Factory work uses the repository's existing Project, but a running Rocky headless environment alone does not prove that a coder or reviewer can safely build and test the repository. Preparation records accepted setup source, administrator-provided shared prerequisites, and separate readiness for each unprivileged Factory role.

Preparation is for a repository maintainer with current native code-write authority and a Project administrator. First, select the repository's setup files and requirements at an exact source revision, then explicitly accept that selection. The accepted inputs cover the setup entry points, effective referenced configuration, required tools and versions, writable build paths, services and readiness checks. Issue text and an agent's suggestion cannot approve setup on their own. If no source files are selected, preparation applies only to the accepted source commit.

The Project administrator separately reviews privileged effects and the shared environment: installed packages and runtimes, root-owned configuration, service definitions, mounts, ports, persistent data and assigned Factory resources. Provide missing shared prerequisites through normal Project administration. Repository setup runs under the assigned coder or reviewer account, without root or wheel privileges. Provider and Factory publication grants are separate from environment setup and are not given to setup commands.

After acceptance and administrator preparation, run readiness for the assigned coder and reviewer. Each role gets its own checkout and private setup state. Readiness confirms the actual tools and versions, writable build and dependency paths, assigned service access and a repository-specific smoke check. A coder's successful setup is not evidence that a fresh reviewer checkout is ready. Factory work can proceed only when the required role checks succeed for the accepted inputs and current Project state.

If a required prerequisite is missing, preparation reports what the administrator needs to provide and waits; it does not grant an agent elevated access or replace the Project. If setup fails or times out, inspect the recorded step and partial effects before retrying. Retry a known safe step only after its prior processes have stopped. Do not blindly repeat shared migrations or delete human data. An uncertain request keeps its original preparation identity for inspection and retry.

Changing a selected setup file, an effective referenced input, an accepted requirement or a required human authority invalidates the affected readiness. Reaccept the changed exact source and repeat the relevant checks. Before shared maintenance, hold affected Factory work, stop its runs and settle credential return; then retain the same Project root, make the change and record fresh readiness. A hold does not authorize rebuilding the environment or resetting persistent data. See [Project maintenance](../70-Operate/30-project-maintenance.md) for retained-root refresh.

Preparation is not the same as enabling or funding the Factory. Repository policy, operator capacity, provider sponsorship and usage limits remain owned by [Factory authorization](../40-Factory/20-factory-authorization.md). Human Join and terminal access are covered in [Projects and workspaces](20-projects-and-workspaces.md) and [Workspace terminals](40-workspace-terminals.md).
