## Original investigation

The current product does not yet provide the requested usable Factory experience. This investigation records **62 distinct findings** in the actual implementation: functional defects, misleading presentation, and unfinished agreed user journeys. These are not 62 equally severe bugs, and this is not a claim that every defect in the repository has been found.

The recurring problem is that implementation structure has been mistaken for user-facing completion. A named component is not necessarily a working interaction; a stored association is not necessarily an executed handoff; a finished process is not necessarily a produced plan. The installed UI exposes internal records and controls without consistently delivering the navigation, understandable state, working action and recovery that users expect.

### N3 — P1 — Long Work content expands instead of becoming a usable scroll surface

- Root browser observation: at 1440×900, `.soda-project-content` was 7,265px high with equal scrollHeight; frame/body grew to about 7,318px. A mouse wheel delta of 1,800 over that content left every inspected scrollTop at zero; document scrollHeight was 7,489px. This reproduces the user's inability to scroll to the feed.
- Source: [frontend/spaces/sodaspaces-workspace.css:250](/home/vince/Projects/sodaos/frontend/spaces/sodaspaces-workspace.css:250) combines `overflow:auto` with `overscroll-behavior:contain`; height chains at `:2`, `:5`, `:31`, `:47`, `:89` depend on enclosing flex sizing. [assets/branding/forgejo/components.css:78-84](/home/vince/Projects/sodaos/assets/branding/forgejo/components.css:78) explicitly gives themed body `height:auto`. Native mount at [forgejo-ext/web_src/css/features/extensions.css:22-25,35-55](/home/vince/Projects/forgejo-ext/web_src/css/features/extensions.css:22) supplies flex sizing and minimum height, not a definite maximum. These rules allow the Work container to become as tall as its content, while containment prevents ordinary wheel chaining to the outer document.
- Expected: either one normal document scroll or a genuinely bounded Work scroller; mouse wheel, touch and keyboard must reach the last post.
- Confidence: installed failure AND cause confirmed. Root's browser-only override setting `.soda-project-content.style.overscrollBehavior='auto'` immediately allowed the same wheel interaction to move the document from 0 to 1,100px. Do not blame `#sodaspaces-drawer .sodaspaces-content` in `sodaspaces.css:36` merely because it says overflow:hidden—the user was on the full-page mount. This override demonstrates the trapping rule; the intended long-term scroll ownership still needs a deliberate layout choice.

## Why the existing checks missed this

The repository has meaningful tests for terminal retention, setup routes, provider dialogs and individual result parsing. Those do not establish the whole user journey. Concrete gaps exposed here are:

- A browser helper that automatically scrolls a target into view can pass while real wheel scrolling is trapped. Geometry checks using `scrollIntoViewIfNeeded()` do not exercise that interaction ([tests/frontend/native-container-geometry.test.ts:337](/home/vince/Projects/sodaos/tests/frontend/native-container-geometry.test.ts:337)).
- Feed tests assert named sections, labels and payload contents, but the presence of `soda-feed-card` does not establish a border, readable spacing or agreement with the approved design ([tests/frontend/factory-feed-browser.test.ts:174](/home/vince/Projects/sodaos/tests/frontend/factory-feed-browser.test.ts:174)).
- Dialog close/reopen within the same component is different from a page reload that loses its enrollment ID. The latter exposes the broker's pending enrollment dependency.
- A successful settings request is insufficient when the submitted payload silently removes previously configured fields. A meaningful check edits one setting and verifies preservation of the others.
- A passing CLI process and a returned credential are not an accepted plan, an actionable issue, a changed app, or a successful user journey. The current presentation collapses several of these distinctions.

The useful acceptance bar is a small number of complete human interactions: open the correct project URL, scroll/read distinct posts, submit and recover a request, watch it reach the right work, inspect truthful failures, find the resulting app, and return after reload without losing context. Each confirmed defect above has a specific trigger to check when repaired. Broad reruns of unrelated passing suites are not required to begin those repairs.
