## Execution and completion rules

1. Dependencies below require accepted input evidence for integration, not a started worker or a task label. Disjoint preparatory/source work may start against an explicitly released contract; it cannot claim integration/native acceptance before its dependencies. The extra native release gates apply to runtime activation and qualification, not unrelated domain/Store/UI work.
2. A task progresses through source complete, serving integrated, focused checks passed, native/installed qualified where applicable, and independent acceptance. The central checklist records the actual stage; a helper-only result cannot close a serving task.
3. Each code packet names exact files, input hashes, producer→controller→transaction→effect→readback→next-stage callers, meaningful negative cases, resource owner, bounded verification budget and expected handoff. Shared schemas, manifests, result/assignment DTOs and Git/index operations have one writer and an acknowledged handoff. Keep active-command handles and 1–5-minute progress/deadline observations; do not duplicate a running command or grow a test suite to avoid diagnosing its failure.
4. Finish affected checks with each task. R47–R52 add cross-task and candidate qualification; they are not permission to postpone unit/transaction checks or repeatedly run broad suites. Use actual PostgreSQL for transactional claims; skipped database tests stay skipped.
5. Native proof precedes dependent runtime rewrites/full builds. Separate CLI jobs, synthetic checkpoints, renamed SDK tests, same-UID file permissions and fixture UI data cannot satisfy P1/P6/P7/P8/P9 or complete serving journeys. Failed design assumptions return with exact evidence to Codex for a bounded owner decision; workers cannot silently weaken the contract or choose a replacement architecture.
6. Bind the execution owner to the human's current handoff. Direct Codex implementation is authorized and does not require an absent Muse coordinator to resume. If Muse is used, preserve the one existing instance and verify its supported continuation/native worker route; do not create a replacement CLI pool. Keep at most three implementation lanes, canonical checkouts and no worktrees, with exact writer/resource custody. Actual model/account/effort and any required Contributor inheritance, command deadlines and source identity require evidence. A restricted continuation is a capability block for that route, not a blanket block on disjoint authorized Codex work.
7. Finite provider/capacity/usage reservations precede calls; no provider runs under database locks. Source planning is not an authorization for paid calls, public release, deployment, broad cleanup or protected-appliance mutation. Existing specific authorizations remain in force; release approval is sought only when the concrete batch is reviewable.
8. Completion means current production wiring plus decisive evidence and independent acceptance, focused commits, truthful docs and released writers/resources. A precise external case remains open without blocking unrelated qualified core work. No percentage substitutes for this.
9. Recheck actual input availability after cleanup or restart; a retained receipt does not prove its former image, VM disk or cache still exists. A changed source/contract/pin/fixture invalidates affected downstream receipts. Requalify the changed joins before further progression, including any R49 proof affected by R54 corrections, rather than reusing a stale success or blindly repeating every suite.

### Why this order

The [dependency validation](../../.artifacts/muse-factory-workflow/reviews/dependency-order-20261018-01a1470a/validation.json) and [derived graph](../../.artifacts/muse-factory-workflow/reviews/dependency-order-20261018-01a1470a/graph.json) bind this revision: 55 unique tasks, no cycles or unknown references, every prerequisite before its consumer, and all 54 other tasks feeding R55. All 365 requirement keys/texts and the existing task checkbox states are preserved. These are planning checks, not implementation acceptance.

- **Establish inputs first:** R01 releases the actual executor/contracts. R02 repairs the current Fountain regression; R07/R08/R09 establish native control, exclusion and transport; R10 releases typed contracts. R44 qualifies Project/provider foundations before live dispatch. R50 proves the protected release mechanism independently with narrow development inputs, as original RT01 requires.
- **Build the common workflow before its consumers:** R11 precedes semantic planning and investigation. Native scheduling and trusted checkpoint production precede publication and current-tuple qualification. Product Lead/Architect, Builder, Inspector/Fixer and Strategist/Test Pilot controls compose the already established owners; R34 consumes R33 singleton-Fixer output rather than inventing another executor.
- **Join every route before merge:** R21 base-advance correction, R24 clear/Jev acceptance and R25 exact native CI all feed R26. Review and CI can progress independently. Completion then feeds the post-completion reassessment fence and protected adoption. R21 is required for final closure through this chain.
- **Compose before freezing:** R47/R48/R49 verify the serving/native/installed development joins. R54 finishes source/caller/selector/docs cutover before R51 creates candidate bytes. R50 supplies the tested admission mechanism; R52 collects exact shipping-byte evidence and R53 consumes it for final publication/download proof. R50 never waits for its future candidate.
- **Keep real inputs explicit:** Before a live trial, bind actual harness/model/account/authority, approved preparation, bounded funding and fixture custody. Before R51, resolve the pipeline's required immutable Fountain/component manifests and bytes, including any separately authorized input-component publication. Final product publication at R53 cannot supply an input needed earlier to build the candidate. Optional external Tailnet enrollment holds its named R46 cases; it does not block unrelated core work.
- **Close the whole graph:** R55 depends transitively on all other 54 tasks. Independent acceptance, exact evidence and final resource release remain necessary; a clean DAG or a reviewed task definition is not implementation acceptance.
